# 구현 범위와 근거

> 영문 원본: `docs/agent/SCOPE.md`. 함께 갱신합니다.
> 우선순위: **Must** (12/31까지 반드시) / **Should** (가능하면) / **Could** (여유가 있거나 1월 이후)

각 기능이 **어떤 역량을 보여주는지**와 **무엇으로 증명하는지**를 같이 적었습니다. 면접에서 "왜 이걸 만들었나요?"라는 질문에 바로 답할 수 있게 하는 것이 목표입니다.

## 역량 태그

| 태그 | 역량 | 관련 공고 키워드 |
|---|---|---|
| `ARCH` | 아키텍처 설계 (서버 분리, 계층, 패턴, 서버·클라 관심사 분리) | 서버 아키텍처 직접 구축, 프레임워크 설계 |
| `NET` | 네트워크 이해 (TCP, 비동기 I/O, 패킷, 세션, 지연·재접속) | 네트워크 프로그래밍, TCP/IP, IOCP/epoll |
| `CONC` | 동시성·멀티스레드 (경쟁 조건, 락, Actor, 원자 연산) | 멀티스레드, 비동기 프로그래밍 |
| `DB` | DB 설계와 트랜잭션 (스키마, 인덱스, 격리 수준, 마이그레이션) | RDBMS 설계, 스키마 변경, 무손실 마이그레이션 |
| `CONS` | 정합성·멱등성 (중복 처리 방지, 원장, 서버 권위) | 라이브 서비스 경험 |
| `PERF` | 성능 (부하 테스트, 병목 분석, GC, 캐시) | 대규모 트래픽, 성능 개선 |
| `LIVE` | 라이브 운영 (운영툴, 점검, 핫리로드, 장애 대응) | 라이브 운영, 운영 도구·백오피스 |
| `SEC` | 보안 (인증, 치트 방지, 비밀값 관리) | |
| `QA` | 테스트와 품질 (통합 테스트, CI) | 유닛 테스트, 코드 리뷰, 품질 관리 |
| `OPS` | 인프라·DevOps (Docker, CI/CD, 클라우드 배포, 모니터링) | AWS, Docker, CI/CD, IaC |
| `CLI` | 클라이언트 이해 (Unity 연동, 코드 공유) | Unity, 클라이언트 연동 |

## 1. 플랫폼 기반

| # | 기능 | 우선순위 | 구현 내용 | 역량 | 증명 |
|---|---|---|---|---|---|
| P1 | 서버 구성 | Must | API(ASP.NET Core) / Realtime(TCP) / Chat(Redis Pub/Sub) / Shared(Unity와 공유)로 분리 | `ARCH` | 아키텍처 다이어그램, ADR |
| P2 | 계층 구조 + Unit of Work | Must | Controller → Service → Repository. Dapper 위에서 여러 Repository를 하나의 트랜잭션으로 묶는 UoW 직접 구현 | `ARCH` `DB` | 코드, ADR (JPA의 `@Transactional`과 비교) |
| P3 | Unity 코드 공유 | Must | 패킷·DTO를 로컬 UPM 패키지로 만들어 서버와 Unity가 같은 소스를 컴파일 | `ARCH` `CLI` | 리포지토리 구조 |
| P4 | 에러코드 체계 | Must | 게임 로직 실패는 예외 대신 범위별 에러코드(Result)로 반환. 응답 공통 포맷 | `ARCH` | API 명세 |
| P5 | 설정과 비밀값 | Must | Options 패턴 + 시작 시 검증, user-secrets, GitHub Secrets | `SEC` `OPS` | 설정을 잘못 넣으면 서버가 뜨지 않음 |
| P6 | 구조화 로그 | Must | `[LoggerMessage]` 소스 생성기, 요청 trace id. 시스템 로그와 게임 로그(재화 변동) 분리 | `LIVE` `PERF` | 로그 예시 |

## 2. API 서버 (게임 경제)

| # | 기능 | 우선순위 | 구현 내용 | 역량 | 증명 |
|---|---|---|---|---|---|
| A1 | 게스트 로그인 + 세션 | Must | JWT 발급, Redis 세션, **중복 로그인 시 기존 세션 강제 종료** | `SEC` `ARCH` | 통합 테스트 (두 번째 로그인 → 첫 세션 무효) |
| A2 | 재화 + 원장 | Must | **유료/무료 다이아 분리**, 잔액 테이블 + 변동 원장(쌓기만 함), 조건부 UPDATE(`WHERE gold >= ?`)로 음수 방지 | `DB` `CONS` | 동시 차감 테스트: 100건 동시 요청 → 잔액이 정확하고 음수가 되지 않음 |
| A3 | 캐릭터 가챠 | Must | 서버가 관리하는 확률 테이블, **천장(pity)**, **확률 공시 API**, 뽑기 로그 | `CONS` `DB` | 10만 회 시뮬레이션으로 실제 분포가 공시 확률과 같은지 검증 (확률형 아이템 규제 대응) |
| A4 | 멱등성 | Must | 가챠·구매 요청에 요청 ID. UNIQUE 키 + 결과 저장. 재시도하면 같은 결과를 돌려줌 | `CONS` `DB` `NET` | 같은 요청 ID로 동시 5건 → 1건만 처리. 디버그 패널의 "5번 보내기" 버튼으로 시연 |
| A5 | 인벤토리 + 강화 | Must | 수량형 아이템과 개별 장비 테이블 분리, 강화는 `SELECT ... FOR UPDATE` | `DB` `CONC` | ERD 설계 근거, 동시 강화 테스트 |
| A6 | 우편 | Must | 보상 지급, 만료, 중복 수령 방지, `(user_id, expired_at)` 커버링 인덱스 | `DB` `PERF` | 인덱스 적용 전후 `EXPLAIN`과 응답 시간 |
| A7 | 상점 | Must | 구매에 멱등성 적용, 한정 상품 재고 (DB 락과 Redis 방식 비교) | `CONS` `CONC` | 재고 초과 판매 방지 테스트 |
| A8 | 스테이지 결과 검증 | Must | 전투는 클라이언트가 진행하고 서버는 결과만 검증 (전투력 대비 클리어 시간, 보상 상한) | `SEC` `ARCH` | 조작한 결과 요청 → 거부되는 테스트 |
| A9 | 보상 지급 (Strategy 패턴) | Must | `IRewardGranter`를 재화·아이템·캐릭터별로 구현. 우편, 가챠, 상점, 레이드 보상이 같은 로직을 사용 | `ARCH` | 새 보상 타입을 추가할 때 기존 코드를 수정하지 않음 |
| A10 | 스태미나·일일 리셋 | Should | 타이머 없이 마지막 갱신 시각으로 계산(lazy), `TimeProvider`로 시간 주입 | `ARCH` `QA` | 시간을 조작하는 테스트 |
| A11 | 월드 보스 | Should | 전 유저가 HP 하나를 공유. **Redis Lua로 원자적 차감**, 막타 1명 판정, 기여도 랭킹(Sorted Set) | `CONC` `PERF` | 봇 1,000명 동시 타격 → HP 정확히 0, 막타 1명 |
| A12 | 시즌 랭킹 + 보상 배치 | Could | 시즌 종료 시 순위별 보상을 배치로 지급 | `LIVE` `DB` | |
| A13 | 길드 | Could | 가입·정원 경쟁 조건 처리 (version 컬럼으로 낙관적 락), 기부 | `CONC` `DB` | 정원 초과 가입 방지 테스트 |
| A14 | 출석 | Could | 일일 보상 | | |
| A15 | 결제 Mock | Could | 영수증 검증을 인터페이스로 분리, 이중 지급 방지, 결제 원장 | `CONS` `ARCH` | |

## 3. 실시간 서버 (협동 레이드)

| # | 기능 | 우선순위 | 구현 내용 | 역량 | 증명 |
|---|---|---|---|---|---|
| R1 | TCP 서버 | Must | `Socket` + `System.IO.Pipelines`로 직접 구현. 세션, 송신 큐, 패킷 조립(길이 + ID 헤더), MemoryPack 직렬화 | `NET` | 코드, 패킷 명세. **IOCP/epoll과 같은 구조로 설계해서 C++ 면접에서도 설명 가능** |
| R2 | 하트비트·타임아웃 | Must | 끊긴 연결 감지 | `NET` | |
| R3 | 입장 토큰 | Must | API 서버가 발급하고 실시간 서버가 검증 (서버 간 신뢰) | `SEC` `ARCH` | |
| R4 | 매칭 | Must | Redis 매칭 큐 → 방 생성 → 입장 | `ARCH` `CONC` | |
| R5 | Room JobQueue (Actor + Command) | Must | Room마다 `Channel<T>` 큐 하나. 패킷을 Command로 만들어 순서대로 처리 → **락 없이 Room 상태 일관성 유지**. Room 안에서는 DB·HTTP를 직접 호출하지 않음 | `CONC` `ARCH` | 부하 중에도 상태가 깨지지 않음 |
| R6 | Room·보스 상태 머신 | Must | 대기 → 카운트다운 → 전투 → 결과 → 종료. 상태별로 받을 수 있는 패킷 제한 | `ARCH` `SEC` | 잘못된 상태에서 보낸 패킷 → 거부 |
| R7 | 서버 권위 전투 | Must | 보스 HP와 데미지 판정은 서버만 함. 클라이언트는 입력만 보냄 | `NET` `SEC` | |
| R8 | 재접속 복구 | Must | 끊겨도 일정 시간 자리 유지, 재접속하면 현재 상태 동기화 | `NET` `LIVE` | 시연: 네트워크 끊기 → 재접속 |
| R9 | 결과 반영 + Outbox | Must | 레이드 결과를 API로 보고 → DB 커밋 후 Redis(랭킹) 반영. 서버가 죽어도 유실되지 않게 Outbox 사용 | `CONS` `ARCH` | 반영 중 장애를 주입하는 테스트 |
| R10 | 무중단 종료 (graceful shutdown) | Must | 배포 신호를 받으면 새 방 생성 중단 → 진행 중인 레이드가 끝난 뒤 종료 | `LIVE` `OPS` | 배포 중 레이드 유지 시연 |
| R11 | 레이드 연습장 + DPS 측정 | Should | 허수아비 + 서버 판정 데미지를 실시간 집계 (레이드 기여도 로직 재사용) | `NET` `CLI` | 서버 판정이 화면에 보임 |
| R12 | 채팅 서버 | Should | Redis Pub/Sub. 일반 채팅 + 서버 공지 | `ARCH` `NET` | |
| R13 | TLS 성능 비교 | Should | `SslStream`을 설정값으로 켜고 끔. 켰을 때와 껐을 때 CPU·지연 비교 | `NET` `SEC` `PERF` | 부하 테스트 수치 |
